# ADR 0004: Возврат хранения на SQLite/aiosqlite (отмена ADR 0002)

Дата: 2026-08-30
Статус: принято
Суперседит: ADR 0002 (PostgreSQL в Docker Compose, бот на хосте)

## Контекст

ADR 0002 (2026-08-24) перевёл хранение с SQLite на PostgreSQL в Docker
Compose: контейнер `db`, volume `pgdata`, порт на loopback, цепочка
миграций, адаптированная под Postgres (включая `users.telegram_id → BIGINT`).
На практике PostgreSQL в Docker для этого проекта не оправдал себя:
дополнительный контейнер, возня с портами (локальный 5432 занят), требования
medium-процедуры запуска (`up -d` → healthy → миграции), мультипроцессные
ограничения — всё это оказалось дороже, чем польза от СУБД в текущем объёме
(одиночный long-polling бот, редкая запись, крошечная выборка данных).
Владелец проекта не оценил Postgres и хочет вернуть простой, переносимый
SQLite-файл.

## Решение

1. Хранение возвращается на SQLite через `aiosqlite` (async-драйвер уже в
   зависимостях и так использовался для тестовых баз).
2. `compose.yaml` и образ PostgreSQL удаляются из репозитория; бот снова
   запускается только через `./venv/bin/python main.py` без Docker.
3. Путь к файлу БД задаётся в `.env` как `DATABASE_PATH` (например
   `database/database.db`); `ConfigBot.DATABASE_URL` собирается как
   `sqlite+aiosqlite:///<путь>`.
4. История миграций переписывается с нуля: прежняя цепочка
   (`d86de4 → 6fc3959 → 9c3e2a1b7d4f → f8b2d4c6a9e1 → c4d9e7f2a8b3 →
   e9f4b8c2d6a7 → ecb821d8dbe4`) заменяется единственной начальной
   ревизией, создающей полную текущую схему из `models.py`, плюс сид
   категорий. Все ПГ-специфичные хвосты (`ON CONFLICT`, `BIGINT`) исчезают.
   SQLite не различает ширину целочисленных типов (динамическая типизация),
   поэтому отдельная ревизия про `telegram_id → BIGINT` не нужна.
5. `wait_for_database()` из `main.py` удаляется: SQLite-файлу не требуется
   ожидание готовности.
6. Зависимости: убираются `psycopg`, `psycopg-binary`; `aiosqlite`
   остаётся и становится единственным драйвером.
7. Тесты: удаляется Postgres-only сценарий `test_telegram_id_bigint.py`
   (SQLite с динамической типизацией по определению не может переполнить
   целое, баг невоспроизводим). Остальные тесты уже на SQLite-базах —
   без изменений.
8. `.env.example` и документация (README, AGENTS) обновляются под SQLite.

## Последствия

- Исчезает стратегия бэкапов уровня Postgres и контейнер; бэкап снова
  сводится к копированию одного `.db`-файла.
- Возвращается ограничение одного процесса записи, но для одиночного
  long-polling бота оно не актуально.
- Webhook-режим (сделан отдельно от хранения) не зависит от движка БД и
  остаётся на месте.
- План оплаты (ADR 0003, раздел «Оплата» в CONTEXT.md) ортогонален
  хранению и сохраняется без изменений.
- `users.telegram_id` продолжит объявляться как `BigInteger` в модели
  (семантически правильно и безопасно на SQLite), хотя на Postgres-уровне
  эта ревизия больше не существует.
