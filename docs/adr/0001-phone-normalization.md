# ADR 0001: Нормализация телефона покупателя через phonenumbers с регионом по умолчанию RU

Дата: 2026-08-22
Статус: принято

## Контекст

Телефон покупателя — единственный канал связи для подтверждения заявки.
До этого решения он хранился как произвольная непустая строка: опечатки и
локальные форматы делали номер непригодным для связи. Аудитория бота — весь
мир, но явных кодов страны в локальных записях (`8900…`, `900…`, `0…`) нет,
и поддерживать правила набора всех стран вручную невозможно.

## Решение

1. Для разбора, проверки структуры и нормализации телефона используется
   библиотека `phonenumbers` (порт Google libphonenumber).
2. Любой принятый телефон хранится в международном формате E.164
   (например `+79001234567`).
3. Номера без `+` разбираются с регионом по умолчанию **RU**. Это умолчание
   парсинга, продиктованное бизнес-контекстом, а не ориентацией бота только
   на Россию; покупатель из другой страны обязан писать номер с `+`.
4. Нераспознанный номер не отклоняет заявку: покупателю предлагается
   повторить ввод с подсказкой указать код страны через `+`. FSM остаётся
   в том же состоянии, отдельный шаг «укажите страну» не вводится.

## Причины

- Справочники кодов стран и шаблонов номеров меняются; libphonenumber
  сопровождает их сообщество, а не мы.
- E.164 как каноническая форма делает телефоны сравнимыми, уникальными
  и пригодными для набора/мессенджеров без дополнительной обработки.
- Повторный ввод дешевле диалога уточнения страны: один лишний шаг FSM
  ломал бы основной сценарий оформления заявки ради редкого случая.

## Последствия

- Новая зависимость проекта (~30 МБ метаданных библиотеки).
- Все новые записи `orders.customer_phone` — только в E.164; исторические
  записи остаются как введены (обратная миграция не планируется).
- Валидные, но необычные номера могут быть отвергнуты метаданными
  библиотеки; риск принимается в обмен на отсев опечаток.
- В тестах используются шаблонные номера из тестовых данных libphonenumber,
  а не реальные номера людей.
