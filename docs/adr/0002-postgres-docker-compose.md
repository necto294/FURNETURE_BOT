# ADR 0002: PostgreSQL в Docker Compose, бот на хосте

Дата: 2026-08-24
Статус: принято

## Контекст

Бот работал на SQLite-файле (`database/database.db`) через aiosqlite.
Для одного процесса с редкой записью этого хватало, но у файла нет
вменяемой стратегии бэкапа и восстановления, параллельная запись
ограничена, а известные пробелы проекта прямо требовали решения
«СУБД + развёртывание». Разворачивать в контейнере решили только СУБД:
бот продолжает запускаться на хосте через venv — отдельный Dockerfile
пока не нужен.

## Решение

1. PostgreSQL запускается через `compose.yaml` в корне: контейнер `db`,
   именованный volume `pgdata`, явная bridge-сеть compose, рестарт-политика
   `unless-stopped`, healthcheck `pg_isready`. Бот в compose не входит,
   поэтому `depends_on` для него бессмысленен.
2. Порт публикуется только на loopback: `127.0.0.1:5432:5432` — бот на той же
   машине достаёт базу через localhost, из внешней сети Postgres недоступен.
3. Данные переносятся чистым стартом: пустой volume → `alembic upgrade head`
   (схема + сид категорий), два товара и админ-пользователь переносятся
   вручную. SQLite-файл сохраняется как архив, обратная миграция данных
   не планируется.
4. Перед переключением вся цепочка ревизий прогоняется с нуля на PostgreSQL.
   Если ревизия окажется диалект-специфичной, её правка до первого прогона
   на Postgres допустима: в мире Postgres применённых ревизий ещё нет;
   SQLite-архив при этом перестаёт побайтово соответствовать файлам
   миграций, что для архива приемлемо.
5. Драйвер — `psycopg` v3 один на всё: SQLAlchemy использует его асинхронно
   (бот) и синхронно (Alembic) с одним URL `postgresql+psycopg://`.
6. Реквизиты БД задаются только разложенными переменными `.env`
   (`POSTGRES_USER/PASSWORD/DB/HOST/PORT`); готовый `DATABASE_URL` отдельно
   не заводится. Compose читает те же переменные сам; URL собирается в коде
   (`settings/config.py`).
7. Бот переживает «БД ещё поднимается» пробой соединения в `main.py` перед
   polling: до 30 попыток `SELECT 1` с интервалом 1 секунда, после исчерпания
   — громкий отказ. Бесконечное ожидание сознательно отвергнуто: оно маскирует
   ошибки конфигурации (неверный пароль выглядел бы как «ждём»).

## Причины

- PostgreSQL даёт нормальные бэкапы (`pg_dump`/`pg_dumpall`), типы,
  конкурентную запись и путь к будущему webhook-развёртыванию; SQLite-файл —
  нет.
- Один драйвер вместо пары «asyncpg + psycopg2» убирает рассинхрон URL между
  ботом и миграциями.
- Разложенные переменные вместо двух независимых полей (для compose и для
  бота) делают пароль однозначным: меняется в одном месте.

## Последствия

- Новая зависимость `psycopg[binary]`; `aiosqlite` остаётся только для
  тестовых временных баз — юнит-тесты гоняются на SQLite-диалекте и не
  покрывают postgres-специфику (принято как ограничение до CI с сервисом БД).
- `alembic.ini` больше не источник URL: `env.py` переопределяет его из
  настроек приложения.
- Первый запуск требует ручного порядка: `docker-compose up -d` → дождаться
  healthy → `alembic upgrade head` → перенос товаров → запуск бота.
- Бэкапы теперь задача уровня Postgres (`pg_dump` по cron); стратегия пока
  не описана — остаётся пробелом.
